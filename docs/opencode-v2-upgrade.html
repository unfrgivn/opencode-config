Upgrade to OpenCode v2

OpenCode v1 and v2 can run side by side. Existing agents, commands, skills, instructions, and supported server configuration remain compatible; the plugin API, server API, and terminal client configuration are the intentional migration boundaries.

1. Close OpenCode first

Finish any active work, stop an existing v2 service if one is installed, then stop remaining OpenCode processes.

(command -v opencode2 >/dev/null && opencode2 service stop || true) && \
(pkill -TERM -x 'opencode|opencode2' || true)

Quit any separately managed background services or agents too, and let everything exit before backing up.

2. Make a small backup

Back up the default config, data, and state directories. This prints filenames as it copies, and may take a while for large history. Cache is re-downloadable, so it is excluded. If you use custom XDG_* paths or OPENCODE_DB, adapt the paths below.

backup_dir="$HOME/opencode-pre-v2-$(date +%Y%m%d-%H%M%S)" && \
umask 077 && \
mkdir -p "$backup_dir/config" "$backup_dir/data" "$backup_dir/state" && \
( [ ! -d "$HOME/.config/opencode" ] || cp -av "$HOME/.config/opencode/." "$backup_dir/config/" ) && \
( [ ! -d "$HOME/.local/share/opencode" ] || cp -av "$HOME/.local/share/opencode/." "$backup_dir/data/" ) && \
( [ ! -d "$HOME/.local/state/opencode" ] || cp -av "$HOME/.local/state/opencode/." "$backup_dir/state/" ) && \
printf 'Backup written to %s\n' "$backup_dir"

The backup can contain credentials, so do not share or commit it. Keep it until v2 is proven. v1 and v2 share the default DB path, so rollback requires restoring pre-upgrade config and data, not only removing an alias.

3. Install the v2 beta CLI

Install only the OpenCode v2 beta CLI.

npm install -g @opencode-ai/cli@beta

After installation finishes, check the version. The reported beta version may look like 0.0.0-beta..., not 2.x.

opencode2 --version

Keep the Homebrew v1 install until the whole migration succeeds.

4. Clean up v1 plugins

Add the Fellowship plugin to your OpenCode configuration before launching v2.

{
  "plugins": ["@unfrgivn/opencode-config"]
}

V1 plugin implementations do not run in v2. Disable any remaining third-party plugins until each has a confirmed v2-compatible release.

  • Add @unfrgivn/opencode-config to the plugins list in opencode.json.
  • Do not remove personal agent, command, skill, MCP, or instruction definitions; supported v1 definitions remain compatible.

5. Launch v2 directly and wait

Run the v2 binary once against your normal profile. Let migration and startup finish before checking anything.

opencode2

OpenCode v2 migrates supported global terminal settings into ~/.config/opencode/cli.json and leaves tui.json unchanged for v1. Project-local terminal settings are not migrated because v2 terminal configuration is global.

Review the generated cli.json for your terminal preferences. Keep the Fellowship package in the plugins list in opencode.json.

6. Verify the service and Fellowship

V2 uses a shared background service. An updated client can reconnect to a service started by an older beta, so compare the client version with the API health response:

opencode2 --version && \
opencode2 service status && \
opencode2 api get /api/health

If the health response reports a different version, restart the service and check again:

opencode2 service restart && \
opencode2 api get /api/health

Inside v2, run /fellowship-status. The package is loaded from your opencode.json plugin list.

  • Status is recent for this startup.
  • The loaded @unfrgivn/opencode-config version matches the one you installed.
  • If /fellowship-status is missing, inspect your plugin configuration.

Then verify package plugins from the CLI:

opencode2 plugin list && \
opencode2 plugin check

7. Alias after success, optional

After v2 starts cleanly, the service version matches, and Fellowship status is correct, optionally make opencode launch opencode2:

printf '\n# Make opencode default to opencode2\nalias opencode="opencode2"\n' >> ~/.wpuserrc && \
source ~/.zshrc

8. Keep v1 until migration succeeds

Do not uninstall the Homebrew v1 package until v2 has migrated, loaded Fellowship, and completed a normal work session. While both versions remain available, keep shared server configuration in supported v1 syntax; v1 may not understand a file converted to native v2 fields. If rollback is needed, quit all OpenCode processes and restore the backup from step 2 before using v1 again.

9. Ask OpenCode to finish the config migration

After v2 and Fellowship are working normally, start opencode2 and send this prompt:

Migrate my OpenCode configuration, including file-based definitions, from the v1 format to the native v2 format. Preserve its behavior and all unrelated settings.

Review the resulting diff before accepting it. Once shared configuration uses native v2 fields, do not launch v1 against it; restore the backup first if you need to roll back.

Local files created or changed

OpenCode v2 creates or changes several files outside the Fellowship plugin repository:

PathPurposeAction
~/.config/opencode/cli.jsonGlobal v2 terminal preferences and CLI-only plugins.Review and keep.
~/.config/opencode/opencode.json(c)Shared v1/v2 server and project configuration.Preserve unrelated settings. Remove or disable only incompatible plugins and accidental duplicate Fellowship entries.
~/.config/opencode/tui.json(c)Legacy v1 terminal configuration.Keep while v1 remains installed. V2 does not read it.
~/.config/opencode/service.jsonPrivate service configuration and authentication.Back up but do not commit, share, or edit by hand.
~/.local/state/opencode/service.jsonRegistration for the running shared service.Do not edit or delete. Use opencode2 service commands.
~/.local/share/opencode/opencode.dbSession and application data shared by v1 and v2.Back up before migration; do not edit.
~/.cache/opencode/packagesDownloaded package plugins.Do not commit. It can be rebuilt if troubleshooting requires it.
Generated Fellowship skill, plugin, schema, and MCP pathsAssets synchronized from the installed package.Do not edit generated remote assets. Keep personal overrides separate.

Troubleshooting, only if needed

Plugins failed to load

Select the failed plugin and press Enter to view its error. Run opencode2 plugin list and opencode2 plugin check, remove leftover _remote_opencode-config_* files using step 3, then restart the service.

If a third-party plugin still fails, disable it until it has a v2 release. Plugin API incompatibilities need a compatible release or configuration update, not repeated cache deletion.

The CLI and service report different versions

Restart the shared service with opencode2 service restart. If it still reports the old version, capture opencode2 service status, the /api/health response, and relevant role=server lines from ~/.local/share/opencode/log/opencode.log.

A saved integration credential fails

Reconnect the integration through OpenCode. Remove a credential only after confirming it is obsolete, and use the OpenCode UI or API rather than editing credential files or the database.

Fellowship status is stale or the package cache looks wrong

Quit OpenCode and its background service, then clear the package cache. Packages will be downloaded again on startup.

rm -rf "$HOME/.cache/opencode/packages/"*

Start opencode2 again and check that /fellowship-status is fresh. If the loaded version is still wrong, open an issue at github.com/unfrgivn/opencode-config/issues with the loaded version and status timestamp.
